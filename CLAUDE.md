# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Requires Node 22+ (a user-local install lives at `~/.local/opt/node22/bin`; add it to PATH if `node` is missing).

- Before `npm run dev` or tests: Postgres must be running — `docker compose up -d` (see root `docker-compose.yml`), exposed on host port **5433** (5432 is often taken by other local Postgres containers).
- `npm run dev` — runs both dev servers via concurrently: Fastify API on :3001, Vite on :5173 (proxies `/api` incl. WebSocket → :3001). The server script runs `prisma db push` first, so schema changes apply automatically.
- `npm run test` — vitest in `shared/` then `server/` (no web tests). Server test files run sequentially (`server/vitest.config.ts`, `fileParallelism: false`): every `buildApp` holds a Prisma pool until the suite's `afterAll`, and parallel files blow past Postgres `max_connections`.
- `npm run test -w server` — one workspace; add `-- -t "name"` for a single test
- `npm run build` — `prisma generate` + typecheck all workspaces + `vite build`. In prod, Fastify serves `web/dist` if it exists.
- `npm run db:seed -w server` — populates a sample dataset (two users `ayse`/`bora`, password `sifre123`, one canvas with a few nodes/edges/commits) through the real `createCanvas`/`CommitService` code path. Not idempotent — run once against an empty DB.

Database: **PostgreSQL** via **Prisma 7** (driver adapter `@prisma/adapter-pg`), run via Docker (`docker compose up -d`). Connection URL comes from `server/.env` (`DATABASE_URL`) read by `server/prisma.config.ts` — Prisma 7 does not read the URL from schema.prisma. There is no boot-time seed: each canvas gets its root-node seed commit when it is created. No migration files: schema changes go through `prisma db push`. To reset dev data: `docker compose down -v && docker compose up -d && npm run dev -w server` (re-runs `prisma db push`).

Tests get isolated DBs from `server/src/testDb.ts`: one `prisma db push` into a template Postgres database per suite, then a cheap `CREATE DATABASE ... TEMPLATE` per test (`testDbFactory().fresh()`, both `fresh()`/`cleanup()` are async), consumed by `await buildApp(url)` from `server/src/app.ts`. `cleanup()` terminates backends and drops every database it created — always disconnect Prisma clients before calling it (see the single merged `afterAll` in `commitService.test.ts`) or `DROP DATABASE` will stall on lingering connections.

## Architecture

TreeMapper is a collaborative development-planning app with an **in-app commit system** (not real git): every mutation is a numbered commit with an author; concurrent conflicting edits land on branches the user resolves.

npm-workspaces monorepo: `shared/` (types + op engine + WS message types), `server/` (Fastify + Prisma), `web/` (Vite + React + React Flow + zustand).

### Multi-canvas & invites

All graph data is scoped to a **Canvas** (`Canvas`/`CanvasMember`/`Invite` models; `canvasId` on Node/Edge/Commit/Branch). Membership is the only access rule: every `/api/canvases/:canvasId/*` route sits behind a preHandler that 404s non-members (`isMember` in `server/src/canvasService.ts`), and joining someone else's canvas is **only** possible via an invite link (`POST .../invites` → token → `POST /api/invites/:token/accept`, idempotent). Canvas creation (`createCanvas`) writes the owner membership and a seed root-node commit named after the canvas. **`POST /api/canvases` requires `groupId`**: every new canvas belongs to a group; permission = group admin OR approved member whose `GroupRoleDef.canCreateCanvas` is true (`memberPermissions()` in groupService — this route is the flag's enforcement point). The `createCanvas()` service function itself stays group-optional (seed/tests); pre-existing group-less canvases keep working but can't gain sub-canvas links. `GroupInfo.canCreateCanvas` tells the dashboard which groups to offer in the (now mandatory) group select.

**Sub-canvas links ("alt kanvas")**: `Node.linkedCanvasId` points a node at another canvas **in the same group**. It is a normal event-sourced node field (`PlanNode`/`NodeFields`, optional on `add_node`, flows through `update_node` → per-field conflicts, invert, diffs all work) — deliberately **no FK** in Prisma: a `SetNull` cascade would write `Node` outside a commit and break `rebuildCheck`; deleting the target just leaves a dangling id rendered as "erişilemiyor". `applyOp` normalizes missing `linkedCanvasId` to `null` on `add_node` replay (legacy commit JSON predates the field — without this every old canvas fails `rebuildCheck`). Same-group validation lives in `CommitService.assertLinkedCanvases`, called from all three arms of `commit()` (fast path, auto-merge, branch landing) but deliberately NOT from `applyCommit` — revert/restore/mergeBranch skip it so historical states pointing at since-deleted canvases stay restorable. Two canvas-scoped reads support the UI: `GET .../preview` (light `CanvasPreview`: name, status-colored node dots, edge index pairs, done/total) and `GET .../info` (a `CanvasInfo` so the web can open a linked canvas without the dashboard); both sit behind the membership preHandler, so a viewer without access gets 404 — the web shows a 🔒 badge and deliberately can't distinguish "no access" from "deleted". Tests: `server/src/subCanvas.test.ts`.

`buildApp` keeps a `Map<canvasId, CommitService>` (`serviceFor`) — one instance per canvas so the commit mutex serializes **per canvas**. Commit numbering is per-canvas: `Commit` has `@@id([canvasId, seq])` and `nextSeq(tx)` computes max+1 inside the write `$transaction` after a `FOR UPDATE` lock on the Canvas row (no autoincrement; the row lock makes seq assignment safe even across multiple server processes — the in-process mutex alone is not). Node/Edge PKs are `@@id([canvasId, id])`.

### Roles & regions

Member roles are `owner | editor | viewer` (`CanvasMember.role`, default `editor` on invite accept). The canvas-scope preHandler sets `req.memberRole`; `requireEditor` 403s viewers on every mutating route, `requireOwner` gates member management (`PATCH/DELETE .../members/:userId`), canvas deletion (`DELETE /api/canvases/:canvasId`), and all region writes. The owner role never changes hands and the owner can't be removed.

**Regions** (`Region`/`RegionMember`) are owner-drawn rectangles on flow-view coordinates — config, NOT part of the event-sourced graph. A node inside a region may only be touched by that region's members (owner bypasses; nodes with null x/y are outside every region). Enforcement: `regionViolation()` in `shared/src/regionGuard.ts` runs over **expanded ops** with a scratch replay (so cascaded `delete_edge`/`delete_node` from a subtree delete are each checked; edge ops check both endpoints; `move_node` checks before AND after positions), and is invoked inside `CommitService.applyCommit` via `assertRegions` — the single choke point covering commit, auto-merge, revert, restore, and branch merge alike. Routes thread an `Actor { userId, role }` in; no actor (seed, engine tests) = unchecked; a violation throws `RegionError` → HTTP 403. The web `stage()` runs the same shared check for instant feedback, but the server stays authoritative. Region/member/canvas changes broadcast `regions`/`members`/`canvas_gone` WS messages; `kick()` in app.ts force-closes sockets of removed users / deleted canvases. Each region also carries `aiAllowed` (bool, default true) and a free-text `description` (owner-editable in `RegionsPanel`): when `aiAllowed` is false the built-in agent may not touch nodes inside that region (regardless of who invokes it) — enforced in `agent.ts` by `filterAiClosedRegions`, which drops the offending intents server-side, keeps the rest, and appends a Turkish note; the description is threaded into the agent prompt as context. This is separate from the membership `regionViolation` guard.

### Event sourcing is the core invariant

The `Commit` table (append-only JSON op arrays) is the **source of truth** for main; `Node`/`Edge` tables are a materialized cache of replaying main-branch commits. `CommitService.rebuildCheck()` asserts they never diverge — tests use it as the oracle. Never write `Node`/`Edge` outside a commit. Branch commits (`branchId != null`) do NOT touch the materialized tables; branch state is always computed by replay (`branchState()`).

- `shared/src/ops.ts` — op vocabulary (`add_node`…`delete_edge`), `applyOp`, `invertOp`. Ops carry before+after / full snapshots → time-travel, revert, diffs. New op types must satisfy `apply(invert(apply(g, op)))` ≡ identity (tested).
- `shared/src/expand.ts` — pure intent → ops expansion (fills `before` snapshots, computes delete cascades: incident edges first, then nodes leaf-first). Server and web preview both use it, so they can't drift. `shared/` has zero runtime deps: id generation is an injectable `genId` (default `crypto.randomUUID()`-based; the web passes its own `c`-prefixed one).
- `server/src/commitService.ts` — expands via shared `expandAll`, checks regions (`assertRegions`), validates via trial replay, applies in a `$transaction`. **A promise-chain mutex (`locked()`) serializes all mutating paths — it is load-bearing**: the service is async, and without it interleaved commits corrupt head numbering. Edge edits are `delete_edge`+`add_edge` with the same id in one commit — there is deliberately no `update_edge` op.
- All mutations go through `POST /api/canvases/:canvasId/commit`; no per-entity write endpoints.

### Co-op, branching, conflict rules

Clients send `baseSeq` (the head they saw) with each commit. If head moved: re-expand against current state and compare target sets against intervening commits' ops (`opsConflict()` in commitService — node add/delete are wildcards, updates/moves conflict per-field, edges per-id). Disjoint → auto-merge onto main as a normal commit. Overlapping (or re-expansion throws) → a `Branch` row is created (named `{username}`, deduped with a `-2`/`-3` suffix by `uniqueBranchName`) and the commit lands there, expanded against `stateAt(baseSeq)`. Merge = `diffStates(main, branchState)` as one main commit ("take branch wholesale"); discard just flips status — branch commits stay in the table, filtered out of main replay by `branchId: null`. `seq` is one per-canvas counter shared by that canvas's main and branches, so main numbering has gaps where branch commits exist — expected.

### Built-in Gemini agent

`POST /api/canvases/:canvasId/agent {prompt, detail?: 'proto'|'detailed', stepwise?: boolean, selectedIds?: string[], selectedRegionIds?: string[]}` (`server/src/agent.ts`; `selectedIds` = nodes the user marked on the canvas (Ctrl/Shift+click multi-select, `selectedNodeIds` in graphStore) — the prompt tells the model that "bu/şu adımlar" refers to them; `selectedRegionIds` = regions selected the same way, threaded in with their name/description/`aiAllowed` plus the ids of nodes inside them, merged into the effective selected-node set) — natural-language agent embedded in the server, available on every canvas with no bot user or invite: it gathers state + regions, calls Gemini (`GEMINI_API_KEY` in `server/.env`; 503 if unset; model per detail level — proto `gemini-flash-lite-latest`, detailed `gemini-flash-latest`, overridable via `GEMINI_MODEL_PROTO`/`GEMINI_MODEL`, with automatic fallback to the other model on 404/429/503), parses a JSON `summary`/`diagram`/`layout` response, and lands diagram ops as ONE commit through the normal `service.commit` path with the **requesting user as actor** — so viewer refusal, region checks, and conflict branching apply unchanged. Broadcasting goes through `onOutcome`/`onRegions` callbacks the route passes in (every commit/branch/region change is broadcast the moment it lands). **`stepwise: true`** ("+ Parça parça" toggle in the UI, orthogonal to the detail level — detail keeps picking the model and per-part density) is the exception to "ONE commit": the first call returns part 1's ops plus a `parts` array of remaining part titles (capped at 6 parts total); each remaining part is a separate follow-up LLM call against fresh state (`ŞİMDİKİ PARÇA` block in the user text tells the model to connect to previous parts) and lands as its own commit (`ajan: … (parça i/N)`), broadcast live. A part that branches (conflict) or fails validation stops the loop with a Turkish note; earlier parts stay committed; a part with no ops is skipped. **Region creation**: when the actor is the canvas **owner**, diagram responses may carry `newRegions` (max 4/round, validated rects) — created via `createRegion` as the owner's normal canvas config with `aiAllowed` forced `true`, then filled by that round's ops per the region's name/description; non-owner agents get a "don't use newRegions" prompt rule and any that sneak through are dropped server-side with a Turkish note. **`mode: 'layout'`**: a third response mode, triggered by requests like "zihin haritasını akışa dök" / "her bölgeyi ayrı diyagram olarak diz" — here the model only classifies the request and emits no ops/coordinates; the server computes deterministic layout itself via `buildFlowLayoutOps` (`shared/src/flowLayout.ts`, a pure dependency-free engine): each writable + `aiAllowed` region's nodes are arranged as a tidy tree inside that region's rectangle, in-region `parentId` links become flow edges, no cross-region or duplicate edges are produced, region-less nodes are clustered separately, and closed/unwritable regions are left untouched. **Sub-canvas creation (`newSubCanvases`)**: when the canvas belongs to a group AND the actor (non-viewer) has canvas-create permission there (`memberPermissions().canCreateCanvas`), diagram responses may carry `newSubCanvases: [{nodeId, name, description?}]` (max 3/round; `nodeId` may be an existing node or one added in the same round). The server creates each canvas via `createCanvas` in the same group (owner = requesting user), appends an `update_node {linkedCanvasId}` intent to that round's ops **after** `filterAiClosedRegions` (link lands in the same commit through the normal `assertRegions`/`assertLinkedCanvases` path; unknown/already-linked/AI-closed-region nodes are dropped with a Turkish note before any canvas is created), then — once the round's commit stands — fills each new sub-canvas with ONE extra LLM call committed into it via `serviceFor(subId)` (`ajan: alt kanvas planı`, actor owner); a failing fill only appends a "doldurulamadı" note, never fails the parent commit. Model-written `linkedCanvasId` inside ops is stripped in `parseModelOutput` — linking happens exclusively through `newSubCanvases`. Unpermitted/groupless contexts get a "don't use newSubCanvases" prompt rule and server-side dropping, mirroring `newRegions`. The model call is an injectable `Llm` function (tests pass a fake; see `agent.test.ts`). Op failures come back as a Turkish error `reply`, not an HTTP error.

### Co-Pronoia: multi-agent planning over MCP

A second canvas/group **type** (`Canvas.type`/`Group.type`, plain strings `'plan'` (default) | `'co-pronoia'`, validated in routes — never Prisma enums): external MCP agents propose plans in parallel and a **supervisor agent** approves them; nothing else changes for `'plan'` data. A co-pronoia canvas can only be created inside a co-pronoia group (enforced in `canvasRoutes.ts`); the same group can also hold normal canvases. Human members keep the full normal UI flow (push/branches/Gemini agent) on co-pronoia canvases — the only new restriction applies to MCP tokens.

- **Agent roles** (`AgentRoleDef`, `server/src/agentRoleService.ts`): one model, `groupId null` = site template (admin-managed via `/api/admin/agent-roles` + AdminPanel "Ajan Rolleri" tab), non-null = group role (`/api/groups/:groupId/agent-roles`, `requireManageRoles`-gated; `AgentRoleEditor.tsx` is the shared UI, parameterized by an `AgentRoleApi` adapter). A role = name + `persona` text (served verbatim to the agent via `get_brief`) + `isSupervisor` flag. The two scopes cannot touch each other's rows (service filters by exact `groupId`).
- **Agent tokens** (`AgentToken`): canvas-scoped API keys, owner-minted from the canvas `CoPronoiaPanel` (`POST .../agent-tokens`, canvas must be co-pronoia, every role must be site-level or the canvas's group). Raw value `tma_<nanoid(32)>` is returned ONCE; the DB stores `sha256` hex (`tokenHash @unique`) — deliberate deviation from `Session` (which stores raw ids): these are long-lived show-once keys, and sha256 is deterministic so `findUnique` lookup works. Revoke sets `revokedAt` (row kept — proposals keep provenance); deleting a role or the minting user cascades tokens away, `deleteCanvas` deletes tokens+proposals explicitly (first entries in its `$transaction`).
  - **Multi-role tokens ("one MCP connection, many agent roles")**: a token can carry more than one role — e.g. one connection acting as both a supervisor and a technical agent — so a group with N roles doesn't need N separate MCP connections. `AgentToken.roleId`/`.role` stay as the **primary/default role** (unchanged column, backward compat); the full role set is a join table, `AgentTokenRole(tokenId, roleId)`, populated with every selected role at mint time. Deliberate migration-free design: rows minted before this feature have zero `AgentTokenRole` entries, so role resolution (`agentRoleService.resolveAgentToken`/`rolesOf`) falls back to the single primary `role` whenever the join table is empty for a token — no backfill script needed, `prisma db push` is enough (rejected the alternative of dropping `roleId` entirely, which would have required a real migration to preserve existing rows). `AgentTokenInfo.roles` (`{id,name,isSupervisor}[]`) is the full set; `isSupervisor` on the DTO is true if ANY assigned role is. Mint (`POST .../agent-tokens`) accepts `roleIds: string[]` (≥1, ≤10, each validated same as before); the legacy single `roleId` body is still accepted and converted to a one-element array so old clients keep working. `list_agents` exposes `roles` per token so a connection's multi-role-ness is visible from MCP too.
  - **Rotate**: `POST .../agent-tokens/:id/rotate` (owner-only, same gate as mint; `agentRoleService.rotateAgentToken`) replaces the row's `tokenHash` with a fresh secret and clears `lastUsedAt` — `label`, roles (primary + join rows), `createdBy`, and all `proposals`/`claims` FKs are untouched (same row id), so history/provenance survives; the old secret is invalid the instant the hash changes. A revoked token cannot be rotated (Turkish refusal — revoke is meant to be final). Response shape mirrors mint: `{ token, secret }`. Web: each token card in `CoPronoiaPanel.tsx` has a "🔄 Anahtarı yenile" button (confirm dialog), and shows the new show-once secret + ready `.mcp.json` snippet inline via the same `SecretReveal` component used at mint time (keyed per-token so several can be open at once).
- **MCP endpoint** (`server/src/mcp/`): `POST /api/mcp`, exempted from the session-auth hook in app.ts, guarded by `Authorization: Bearer tma_...` → `resolveAgentToken` (401 on unknown/revoked; also bumps `lastUsedAt` at most once per 60s — the panel's presence dot; the resolved token carries a `roles: AgentRoleDef[]` array — see multi-role tokens above). **Stateless** Streamable HTTP: every request builds a fresh `McpServer` (`buildCoPronoiaServer`) + `StreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })`, then `reply.hijack()` + `handleRequest(req.raw, reply.raw, req.body)` (third arg is mandatory — Fastify already consumed the body). GET/DELETE → 405; no server push — instead `wait_for_changes {sinceSeq?, proposalIds?, timeoutMs?}` is an in-request long-poll tool (all tokens, read-only): it returns immediately when head passes `sinceSeq` (default: head at call time) or a watched proposal's status/updatedAt changes vs the call-time snapshot (`proposalIds` omitted = watch all, new proposals count), else waits up to 25s (cap safely below Node/proxy response timeouts; the hijacked reply stays open) and returns `timedOut: true`. Waiters sleep on `CanvasEvents` (`server/src/canvasEvents.ts`), a canvasId-keyed emitter fed from the `broadcast` choke point in app.ts on `commit`/`branch_created`/`branch_resolved`/`proposals` messages — a signal only triggers a DB re-read, there is no DB polling loop. The brief tells agents to use it instead of polling `list_proposals` (which stays for the initial read/back-compat). Supervisor tools (`approve_proposal`, `reject_proposal`, `request_changes`, `create_region`) are *registered* whenever ANY of the token's roles is a supervisor, so `tools/list` honestly reflects capability; non-supervisor connections get method-not-found. Intent inputs are validated by a zod discriminated union (`mcp/schemas.ts`) pinned to the shared `OpInput` type via `satisfies`.
  - **Acting-role selection**: role-sensitive tools (`get_brief`, `submit_proposal`, `update_proposal`, `claim_region`, `update_brief`, and the supervisor tools) take an optional `role` input (by **name**, not id) resolved by `mcpServer.resolveActingRole` — single-role tokens default to their one role (a mismatched name is still an error); multi-role tokens **require** it, returning a Turkish error listing the connection's role names if omitted or unknown. `get_brief` additionally lists ALL of the connection's roles (name + supervisor flag) so the agent knows what it can act as; its version-hash signature (used for the `knownVersion` "unchanged" short-circuit) now covers the full role set, not just the acting role, so re-minting/rotating with a different role set busts the cache. Supervisor tools additionally require the *resolved* role to be a supervisor (`resolveSupervisorRole`) — a multi-role connection cannot approve while acting as its non-supervisor role. `submit_proposal`/`update_proposal` stamp `PlanProposal.roleName` (and `claim_region` stamps `NodeClaim.roleName`, a new column, default `""` for pre-feature claims falling back to the token's primary role at read time) with the *resolved* acting role's name, not the token's primary role — so provenance reflects which hat the agent wore for that specific action.
- **Proposals** (`PlanProposal`, `server/src/proposalService.ts`): agents have NO commit tool — `submit_proposal {title, summary, intents, baseSeq, role?}` stores intents as JSON (same pattern as `Commit.ops`) after a trial `expandAll` against current state (early feedback only; authoritative checks rerun at approval). Status machine: `submitted | changes_requested | withdrawn | rejected | applied`; `update_proposal`/`withdraw_proposal` are own-token + open-status only, update resets to `submitted`. `agentLabel`/`roleName` are denormalized so history survives token/role deletion (`tokenId` is `SetNull`); `roleName` is the *acting* role (see above), not necessarily the token's primary role.
- **The approval choke point**: `approve_proposal` (any token with a supervisor role, acting *as* that role — see acting-role selection above) runs the stored intents through the normal `serviceFor(canvasId).commit(...)` with **actor = the user who minted the proposing token** (mirrors the Gemini agent's "requesting user as actor") — viewer refusal, `assertRegions`, `assertLinkedCanvases` and `opsConflict` branching all apply unchanged ("supervisor + code check together"). Stale `baseSeq` → the proposal lands on a conflict branch and is marked `applied` + `branchName` with a Turkish note; deleted token / non-member / viewer creator → Turkish refusal, proposal untouched. Commit message: `ajan önerisi: <title> (<agentLabel>/<roleName>, onay: <supervisor>)`.
- **Human surface**: `GET .../proposals` (members), `POST .../proposals/:id/reject` (owner-only cleanup hatch — approve deliberately has NO human/HTTP path). WS: `{ type: 'proposals', proposals }` full-refresh message (regions pattern) broadcast after every proposal mutation; approve additionally broadcasts `commit`/`branch_created` with `clientId: null`. Web: `CoPronoiaPanel.tsx` (multi-role checkbox mint form, per-token role badges + rotate button, live proposal cards, secret shown once with a ready `.mcp.json` snippet), `🤝 Co-Pronoia` toolbar button gated on `active?.type === 'co-pronoia'` (Chrome.tsx), `proposals` state in graphStore (loaded only for co-pronoia canvases).
- Tests: `server/src/copronoia.test.ts` (type gating, role CRUD permission matrix, token mint/revoke, multi-role mint, rotate), `server/src/mcp.test.ts` (raw JSON-RPC over `app.inject` — needs `Accept: application/json, text/event-stream`; auth, tools/list visibility, full lifecycle incl. conflict-branch and refusal paths, multi-role acting-role selection and supervisor enforcement).

### Yerel mod & bulut aktivasyonu

Tek kod tabanı, iki mod (`server/src/mode.ts`: `APP_MODE=local|cloud`, default `cloud`; `isLocal()`, `cloudUrl()`). **`buildApp` modu bir kez, kurulum anında sabitler** (`const localMode = isLocal()`) — testler tek süreçte hem bulut hem yerel app ayağa kaldırdığı için istek anında env okunmaz. Public `GET /api/mode` → `{ mode, activated, cloudUrl }` (auth hook muafiyet listesinde, `/api/site/` gibi); web `modeStore` bundan hangi ekranı çizeceğini bilir.

**Yerel imaj kodu taşımaz, eler (derleme anı kapısı).** Yerelde asla çalışmayacak kimlik/yönetim kodunu imajda tutmak gereksiz saldırı yüzeyidir, bu yüzden mod kapıları **bilerek** şu biçimde yazılır:

```ts
if (!globalThis.__LOCAL_BUILD__ && !localMode) registerAuthRoutes(app, prisma, …);
```

`server/build.mjs` sunucuyu esbuild ile tek ESM bundle'a (`server/dist/server.mjs`) derler ve `--local` verildiğinde `define: { 'globalThis.__LOCAL_BUILD__': 'true' }` ile ilk terimi sabitler: ifade `false`a katlanır, dal ölü koda döner ve **yalnız orada kullanılan modüller bundle'a hiç girmez**. Yerel bundle'da `authRoutes`/`auth` (scrypt, oturum), `googleAuth`, `adminRoutes`/`adminService`, `email` (nodemailer), `agent.ts` (Gemini) ve üyelik/davet route'ları **yoktur**; `server/src/localBundle.test.ts` bunu her koşuda ölçer (ve aynı sembollerin bulut bundle'ında durduğunu doğrulayarak testin kendini kandırmasını engeller).

İki tuzak, ikisi de ölçülerek bulundu — değiştirirken dikkat:
1. **Kapı bir sabit olamaz.** `export const LOCAL_BUILD = …` biçimindeki bir bayrağı esbuild kullanım yerine gömmez; `if (!LOCAL_BUILD && …)` ölü koda dönmez ve eleme olmaz. `globalThis.__LOCAL_BUILD__` bir dot-chain olduğu için `define` doğrudan kapının içine yazar. (`mode.ts`teki `LOCAL_BUILD` yalnız belgeleme/`isLocal()` içindir, kapı olarak kullanmayın.) Çalışma zamanı güvenli: bare identifier olmadığından define verilmeyen ortamda `undefined` döner, ReferenceError atmaz ve karar runtime `localMode`a düşer.
2. **`minifySyntax: true` şart.** esbuild `if (false) …` dallarını yalnız sözdizimi budaması açıkken siler; kapalıyken dal katlanır ama modül bundle'da kalır. (İsim/boşluk minify'ı bilerek kapalı — imajdaki bundle denetlenebilir kalsın.)

`Dockerfile` bu yüzden üç aşamalıdır: build (web + `bundle:local`), deps (`npm ci --omit=dev`), çalışma katmanı yalnız `server/dist` + `web/dist` + üretim `node_modules` + `prisma` şeması/konfigi alır — imajda kaynak dosya, test ve devDependency bulunmaz (947MB → 756MB). Başlangıç komutu npm workspace çözümlemesine girmez: `cd /app/server && prisma db push && node dist/server.mjs`.

| davet linkleri (`/api/invites/*`, `/api/group-invites/*`, `.../invites`) | var | register edilmez (404) |
| kanvas üyeliği (`.../members*`, `.../role-access`, `.../regions/:id/members`) | var | register edilmez (404) — tek kullanıcı daima owner |
| grup üyeliği + iş rolleri (`GroupRoleDef`: `.../members*`, `.../roles*`) | var | register edilmez (404) |
| **ajan rolleri** (`/api/groups/:id/agent-roles`) ve **bölgeler** | var | **kalır** — MCP anahtarı bir `AgentRoleDef`e bağlanır; bölgeler ajan kısıtı/`aiAllowed`/claim için işlevsel |

Erişim yüzeyi yerelde bilinçli olarak sıfırdır: paylaşacak kimse olmadığı için davet/üyelik/rol kodu ne çalışır ne de imajda durur. `registerGroupMemberRoutes` (üyelik/davet/iş rolleri) ile `registerGroupAgentRoleRoutes` (ajan rolleri) bu yüzden **ayrı** fonksiyonlardır — ilki yerelde register edilmez, ikincisi her iki modda da edilir; ortak `manageMembersGuard`/`manageRolesGuard` yardımcıları modül düzeyindedir. Web tarafı da bu uçlara hiç istek atmaz: `modeStore`'daki `isLocalMode()` ile `graphStore.load` üye çağrısını atlar, `Chrome`/`Dashboard`/`RegionsPanel` davet ve üye/rol atama arayüzlerini çizmez (bölgelerin kendisi, AI izni ve açıklaması yerelde de durur).

Yerel kurulumdan `GEMINI_API_KEY` istemek anlamsız (tek kullanıcılık, kurulum-sonrası internet gerektirmeyen bir dağıtım): `registerRoutes` (`server/src/routes.ts`) `localMode` parametresi alır — `app.ts` zaten `const localMode = isLocal()` desenini kurulum anında sabitlediğinden bunu `registerRoutes`e de geçirir, `/agent` route'u `if (!localMode)` ile hiç register edilmez (404, `geminiConfigured`/`GEMINI_API_KEY` kontrolüne hiç gelinmez). Web tarafında `Chrome.tsx`'teki "✨ Ajan" düğmesi ve `App.tsx`'teki `AgentPanel` render'ı `useModeStore().mode !== 'local'` koşuluyla gizlenir. **MCP ajanları (co-pronoia) bundan etkilenmez** — ayrı bir uç (`/api/mcp`), yerelde de çalışır. `Dockerfile`/`deploy/docker-compose.yml`/`.env.example`'da `GEMINI_API_KEY` yerel dağıtımdan tamamen kaldırılmıştır.

**El sıkışma (PKCE benzeri; şifre asla yerele girilmez)**: yerel `GET /api/activation/start` state+verifier üretip pending `Activation` satırını yazar ve tarayıcıyı `${CLOUD_URL}/?aktivasyon=<state>&donus=<yerelOrigin>&kanit=sha256(verifier)`e 302'ler → bulut web'i (`ActivationApprove.tsx`, `?davet=` deseninin eşi) giriş sonrası onay ekranı gösterir → `POST /api/activation/approve` (oturumlu) `Instance` satırını yazar ve `<donus>/api/activation/callback?state&code`e döndürür → yerel sunucu **sunucudan sunucuya** `POST ${CLOUD_URL}/api/activation/exchange {state, code, verifier}` yapar; bulut kodu tek kullanımlık tüketir, `sha256(verifier) === proofHash` doğrular ve `{ user, instanceToken }` döner (`tmi_<nanoid(32)>`, DB'de sha256 — `AgentToken` deseni) → yerel taraf bulut kimliğini yansıtan `User` (passwordHash yok) + "Yerel çalışma alanı" grubunu kurar, `Activation`ı kalıcı yazar. Bulut çağrıları enjekte edilebilir `CloudClient` (`cloudClient.ts`) arkasında — `EmailSender`/`Llm` deseni; `activation.test.ts` sahte istemciyle bulut app'ine `app.inject` üzerinden bağlanır.

**Çekme**: aktivasyondan hemen sonra ve panodaki "☁ Buluttan çek" ile tekrar; bulut `GET /api/instance/canvases` + `GET /api/instance/groups` + `…/:id/export` → yerel `importBundle()` (`canvasImportService.ts`, `POST /api/canvases/import` ile **aynı** gövde). `CloudImport(cloudCanvasId @unique)` sayesinde aynı kanvas iki kez alınmaz; tek kanvasın hatası çekmeyi durdurmaz.

**Gruplar, kanvas türü ve ajan rolleri de çekilir.** Önceden `/api/instance/canvases` yalnız `{id, name}` döndürüyordu: her kanvas yerelde `plan` türüyle tek bir "Yerel çalışma alanı" grubuna iniyordu, dolayısıyla **co-pronoia kanvasları yerelde co-pronoia olarak açılamıyor ve MCP paneli hiç görünmüyordu**. Artık kanvas künyesi `type`+`groupId`, `/api/instance/groups` ise grupları `type` ve grup kapsamlı `agentRoles` (ad/persona/isSupervisor) ile taşır. `syncCloudGroups()` (`activationService.ts`) grupları türüyle yerelde kurar ve `CloudGroupImport(cloudGroupId @id)` ile eşler — `CloudImport`in grup eşi, tekrar çekmede grup ikinci kez kurulmaz (yerel grup elle silinmişse eşleme düşürülüp yeniden kurulur). Ajan **anahtarları** bilerek çekilmez: DB'de yalnız sha256'ları var ve yerel kurulum kendi anahtarını mint etmelidir. Tür `co-pronoia` yalnız hedef grup da co-pronoia ise uygulanır (kanvas route'undaki kuralın eşi), aksi halde sessizce `plan`a düşer; grubu bilinmeyen ya da eski bulut sürümünden gelen kanvaslar eski davranışla çalışma alanına iner ve `listGroups` hatası çekmeyi durdurmaz (geriye dönük uyum).

**Bağlantıyı kaldırma (yerel modun "çıkış"ı)**: yerelde oturum olmadığı için tek kaldıraç aktivasyonun kendisidir. `POST /api/activation/reset` (`resetActivation()`) `Activation` satırını siler; kurulum "etkinleştirilmemiş"e döner, web aktivasyon ekranını çizer ve başka (ya da aynı) bulut hesabıyla bağlanılabilir. `pull` gibi **el sıkışmanın parçası değildir** — app.ts'teki hook muafiyeti onu dışlar, yani yalnız aktive edilmiş kurulum çağırabilir (aktivasyon kalkınca ikinci istek route'a hiç ulaşmaz, 401 olur). `wipe: false` (öntanımlı) veriyi bırakır, `wipe: true` kanvasları `deleteCanvas` yolundan silip grupları/kullanıcıyı ve eşleme tablolarını temizler (`Canvas.ownerId` FK'si restrict — kullanıcıyı doğrudan silmek kısıt ihlali verir). Buna bağlı olarak `completeActivation` artık var olan yerel kullanıcıyı **yeniden kullanır** (e-posta, yoksa kullanıcı adı eşleşmesiyle): veriyi silmeden bağlantıyı kaldırıp aynı hesapla dönmek olağan akıştır ve körü körüne `user.create` e-posta benzersizliğine takılıp 500 veriyordu. Dashboard'da yerel modda "Çıkış" yerine "🔌 Bağlantıyı kaldır" çıkar (iki aşamalı onay: önce bağlantı, sonra veriyi de silme seçeneği).

Modeller: `Activation` (yerel, tek satır `id='singleton'`), `CloudImport` + `CloudGroupImport` (yerel), `Instance` (bulut). Dağıtım: `Dockerfile` `APP_MODE=local` + non-root + HEALTHCHECK, `deploy/docker-compose.yml` (GHCR imajı + Postgres, port **`127.0.0.1`e bağlı** — yerelde giriş ekranı olmadığı için ağa açmak bilinçli tercihtir), `.github/workflows/docker.yml` GHCR'a yayınlar, `render.yaml` `APP_MODE=cloud` verir.

### Auth & WebSocket

Session cookie (`tm_session`) auth: scrypt hashes in `server/src/auth.ts`, routes in `authRoutes.ts`, a global preHandler hook 401s every `/api` route except `/api/auth/*` and `/api/health`. Commits record `authorId` (a null author renders as "sistem").

**Email verification on register** (Google logins skip it — Google verifies email itself): `POST /api/auth/register` no longer creates the user or a session. It validates + checks uniqueness, then upserts an `EmailVerification` row (email PK; holds `username`/`passwordHash`/`displayName`/`codeHash`/`expiresAt`/`attempts`) and emails a 6-digit code (`generateCode()` in `auth.ts`; code hashed with the same `hashPassword`/`verifyPassword` as passwords), returning `{ pending: true, email }`. `POST /api/auth/verify-email {email, code}` checks expiry (10 min), attempts (max 5 → row deleted), and the code; on success it creates the real `User`, deletes the row, and sets the session cookie — same output as the old register. `POST /api/auth/resend-code {email}` regenerates the code (always `{ ok: true }` to avoid email enumeration). Sending is an injectable `EmailSender` (`server/src/email.ts`, mirrors the agent's `Llm` pattern): `defaultEmailSender` uses nodemailer/SMTP (`SMTP_*` env, lazy import) when `emailConfigured()`; otherwise it logs the code to the console in dev only and **never in production** (`isProd()` = `NODE_ENV==='production'`), where an unconfigured register returns 503 instead. `buildApp(dbUrl, { emailSender })` threads a fake sender for tests (`authRoutes.test.ts`). Frontend: `authStore` keeps `pendingEmail`; `LoginView` shows a code-entry step when it's set.

WS (`/api/ws?canvas=<id>`, broadcast-only — mutations stay on HTTP): the handler closes the socket unless the session user is a member of that canvas; broadcasts go only to clients on the same canvas. Server assigns a `clientId` on connect; clients echo it in commit POSTs; broadcasts carry the originator's `clientId` so the originator skips its own `commit` message (it already applied the HTTP response). Connect/disconnect broadcasts `presence` (active usernames, shown as toolbar chips + green dots in the members panel). Message types in `shared/src/wsMessages.ts`. Password change: `POST /api/auth/password` (revokes other sessions).

### Site admin panel

Site-wide admin is a `User.isAdmin` boolean (independent of canvas/group roles), threaded through `resolveSession`/`toAuthUser` so every auth response and `req.user` carries it. All admin endpoints live in a `/api/admin`-prefixed plugin (`server/src/adminRoutes.ts`, registered in app.ts) whose scope preHandler 403s non-admins (the global hook already 401s). Queries/mutations live in `server/src/adminService.ts`; DTOs (`AdminStats`/`AdminUserInfo`/`AdminCanvasInfo`/`AdminGroupInfo`) in `shared/src/types.ts`. Coverage: stats, user list/search with aggregates, promote (one-way: **admin accounts are untouchable** — demote, password set, and delete are all refused for `isAdmin` targets, self included; the only way back is direct DB access, and `bootstrapAdmin` only ever promotes), password set for non-admins (revokes ALL target sessions; deliberately gives Google-only accounts password login), session revocation, user delete (admins refused; owned canvases cascade via `deleteCanvas`, mainline commits keep history with `authorId: null` → "sistem", the user's branches + branch commits are deleted, invites deleted; refused if they're the sole admin of a group that has other members), canvas list/delete/member-role/remove/invite-revoke, group list/delete/member management (reuses `canvasService`/`groupService` functions + `kick()` for WS drops). **Deliberately NO canvas-content endpoints** (`/state`, `/commits`) under `/api/admin` and `memberRole()` is untouched: admins manage metadata only and cannot open/read canvases they aren't members of — do not "fix" this. The admin account bootstraps at server start (`bootstrapAdmin` in `server/src/adminBootstrap.ts`, called from index.ts, NOT from `buildApp` so tests don't need env): `ADMIN_USERNAME`/`ADMIN_PASSWORD` env → create-or-promote, idempotent, never overwrites an existing password; also the recovery hatch if admins lock themselves out. Frontend: `web/src/components/AdminPanel.tsx` (tabs Genel Bakış/Kullanıcılar/Kanvaslar/Gruplar/Görünüm), opened via a `user.isAdmin`-gated 🛡 button in the Dashboard toolbar through `adminStore.open` (no router — App.tsx renders it instead of `<Dashboard/>` when set); `adminApi` group in `api/client.ts`. Tests: `server/src/adminRoutes.test.ts` (elevate via `prisma.user.update` after `registerVerified`).

**Site appearance (login preview image)**: the login screen's illustration is admin-managed via the `SiteAsset` table (key/mimeType/data/url; single key `login_preview`) — site config, NOT canvas data. `server/src/siteAssetService.ts` owns validation; `PUT/DELETE /api/admin/appearance/login-preview` takes either `{dataUrl}` (base64 upload, stored as bytes) or `{url}` (external http(s) address) — never both, and setting one clears the other. Because the login screen renders with no session, reads are public: `/api/site/*` is exempt from the global auth hook alongside `/api/auth/*` and `/api/health`. `GET /api/site/appearance` returns `SiteAppearance {loginPreview}` (either the external URL or `/api/site/login-preview?v=<updatedAt>` for cache-busting), and `GET /api/site/login-preview` streams the bytes. Unset → null → the web falls back to the bundled example `web/public/login-preview.svg` (a hand-drawn fake canvas, not real user data); `LoginView`'s `<img onError>` falls back to it too. **SVG uploads are deliberately rejected** (`ALLOWED_MIME` = png/jpeg/webp/gif): same-origin SVG can execute script. Uploaded bytes are served with `nosniff` + `default-src 'none'; sandbox` CSP for the same reason. Deliberately NOT "pick a real canvas to display" — that would publish private content and require admins to read canvases they aren't members of, breaking the rule above.

### Frontend: dashboard → canvas; one graph store, three views + panels

Login lands on the **dashboard** (`web/src/components/Dashboard.tsx` + `store/canvasStore.ts`): list/create canvases, copy invite links (`{origin}/?davet=<token>`). Opening a canvas sets the API base via `setActiveCanvasId` (in `api/client.ts`) and mounts the graph UI; `← Pano` returns and resets `graphStore`. A `?davet=` URL param is accepted right after login/register in `App.tsx`, then stripped from the URL.

**Push/staging**: mutations do NOT hit the server immediately. `graphStore` keeps `serverNodes/serverEdges` (canonical) plus `pending: OpInput[]`; every view reads the preview (`nodes/edges` = `applyIntents(server, pending)` from `store/applyIntents.ts` — a thin wrapper over shared `expand`+`applyOp` at seq 0, lenient per intent because a WS commit can invalidate a staged intent). The toolbar **Push** button sends all pending intents as ONE commit (`baseSeq` = current head, so the normal auto-merge/branch rules apply); **Vazgeç** drops them. Direct server ops (revert/restore/merge/discard) are blocked while anything is pending. Staged-only entities render with `createdCommit: 0` ("yeni•" badge).

`web/src/store/graphStore.ts` holds canonical state and the WS connection; views derive React Flow props:

- **FlowView** uses persisted `x`/`y`; custom edge component `web/src/components/CurvedEdge.tsx` renders kind styles (flow solid blue, loop orange, dependency dashed purple, relation dotted gray), self-loops (arc over the node), and parallel edges (perpendicular offset by index within the unordered node pair), bidirectional = arrowheads both ends.
- **MindMapView** ignores `x`/`y` — layout computed by `web/src/layout/mindmapLayout.ts` (d3-hierarchy), never persisted. Hierarchy lives in `parentId` on nodes; only free-form connections are `Edge` rows.
- **TimelineView** reuses `CommitList` + scrubber.
- **FlowView also renders regions** as React Flow nodes (type `region`, `zIndex: -10`, id prefix `region:`): translucent rectangles the owner can drag and resize (`NodeResizer` in `RegionNode.tsx`); non-owners see them read-only.
- Side panels (`sidePanel` in store): history, connections (textual edge list with edit/delete), branches (view/merge/discard), members (roles/remove for owner, presence dots), regions (owner: create + per-region member checkboxes).
- Read-only is `useReadOnly()` = time-travel ∨ branch view ∨ viewer role; `stage()` blocks staging accordingly.
- **Linked sub-canvas UI**: `NodeCard` renders a mini-map preview (`SubCanvasPreview`: `canvasApi.preview` → status-colored dot SVG + done/total; 404 → 🔒 "erişilemiyor"; click → `canvasStore.openById`, confirming first if `pending` is non-empty since switching canvases drops staged work). `NodeEditorPanel`'s "Bağlı kanvas" section (only on group canvases) links an existing same-group canvas or creates one (`canvasApi.create` immediately, then stages the `update_node {linkedCanvasId}` — a discarded pending link just leaves an unlinked group canvas). Dashboard's group select is mandatory and lists `groups.filter(g => g.canCreateCanvas)`; with none, the create form is replaced by a guidance note.

Read-only mode is shared by time-travel (`viewingSeq`) and branch viewing (`viewingBranchId`): both load into `viewingState`, `useDisplayedGraph()` picks the right source, `guard()` blocks mutations. `?view=flow|mindmap|timeline` deep-links a view.

UI language is Turkish; keep new user-facing strings in Turkish.
