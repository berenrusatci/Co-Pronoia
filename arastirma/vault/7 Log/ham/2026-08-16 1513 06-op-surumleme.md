4.6 History rewrite politikası

Varsayılan: hiçbir Commit.ops satırını değiştirme.

İzin: yalnız açıkça ilan edilmiş major history epoch operasyonunda.

Bir epoch rewrite'ın minimum koşulları:

original Commit log'unun immutable export'u;

tam DB backup;

transform dry-run;

open branch = 0 veya branch history'nin de aynı epoch migration'ına dahil olması;

source log için hash manifest;

schema-only rewrite ise pre/post tüm historical checkpoint state'lerinin eşitliği;

rollback'in eski DB/log export'una dönüşle gerçekten denenmesi.

Co-Pronoia bugün geçmiş stateAt ve revert sunduğundan Marten'in snapshot-and-truncate modelini normal bakım olarak kullanmak yanlış olur. Marten bunu ancak eski ayrıntılı history artık gerekmiyorsa sunuyor.
https://martendb.io/events/compacting
 — erişim 16.08.2026. 
MartenDB

Efor: bugünkü politika S; gerçekten epoch rewrite yapmak L.
Yapılmazsa: bir bakım script'i history'yi sessizce değiştirip rebuildCheck=true bırakabilir.
Kabul kriteri: normal release/migration kodunda Commit.ops için 0 UPDATE/DELETE; future epoch rewrite varsa backup + dry-run + manifest olmadan script çalışmayı reddetmeli.

4.7 En fazla üç aşamalı migration
Aşama 1 — Sözleşme ve test kapısı

İş: exhaustive field/op descriptor, canonical semantic-invert testi, disk üzerinde v0 fixtures, server persisted-event integration testi.

Desteklenen en eski event: mevcut unversioned legacy (v0).

Fail davranışı: malformed historical JSON → fail-closed; o canvas replay edilmez.

Rollback: yalnız kod/test değişikliği; persisted data değişmediği için doğrudan eski release'e dönüş mümkün.

Release kriteri:

6/6 op legacy fixture;

5/5 derived replay path testi;

new-field compile gate;

new-op compile gate;

mevcut rebuildCheck testleri yeşil.

Efor: M.
Yapılmazsa: stage 2'nin decoder'ının doğru olup olmadığını gösterecek frozen history oracle'ı olmaz.

Aşama 2 — v0 → v1 envelope/upcaster

İş: missing v → 0; CURRENT_OP_VERSION=1; saf 0→1 upcaster; bütün yeni op'larda v:1; bütün DB reads merkezi decoder'dan.

Bugünkü v0→v1 yalnız mevcut default sözleşmesini centralize eder; business semantic change yapmaz.

Bu aşamanın güzel bir rollback özelliği var: top-level ekstra v mevcut runtime switch'leri tarafından kullanılmıyor, dolayısıyla v1 payload diğer alanlar bakımından v0 ile aynı tutulursa eski kod büyük olasılıkla ekstra property'yi görmezden gelir. Bu yalnız v1'in additive-envelope release'i için geçerlidir; gelecekte v2 rename yazıldıktan sonra eski binary'ye rollback güvenli değildir. Bu sonuç repo kodundan çıkarımdır: switch'ler yalnız op.op ve payload alanlarını okuyor (ops.ts:34-102).

Desteklenen en eski: v0.
Fail: v<0, v>1, malformed payload → fail-closed.
Rollback: v1 yalnız discriminator eklediği sürece önceki release'e dönülebilir; ilk v2 breaking payload yazıldıktan sonra değil.

Release kriteri:

yeni DB eventlerinin %100'ü v=1;

v0 fixtures %100 replay;

v=999 %100 reject;

persisted ops için raw JSON.parse decoder dışında 0 adet.

Efor: M.
Yapılmazsa: breaking değişiklik geldiğinde migration altyapısı production history üzerinde ilk kez denenmiş olur.

Aşama 3 — Mevcut bütün olayların doğrulanması

İş: rewrite yok. Read-only scanner bütün Commit.ops kayıtlarını parse → validate → upcast etsin.

Ardından:

bütün main canvases replay;

bütün main canvases rebuildCheck;

bütün open branches replay;

unsupported/malformed event raporu;

version histogram (v0, v1, gelecekte v2...) üretimi.

Desteklenen en eski: v0; v0 desteği kaldırmak için bugün bir gerekçe yok.

Fail: release validation sırasında tek unsupported event bile varsa deploy gate fail-closed. Runtime'da tüm servisi kapatmak yerine etkilenen canvas işlemini fail-closed yapmak makul.

Rollback: read-only aşama; veri rollback'i yok.

Release kriteri:

stored event decode başarısı %100;

unsupported version 0;

main canvas rebuild mismatch 0;

open branch replay failure 0.

Efor: M.
Yapılmazsa: yalnız fixture'ların temsil ettiği geçmiş doğrulanmış olur; gerçek production event çeşitliliği bilinmez.

Bu üç aşamada hiçbir veri rewrite önermiyorum.

5. Açık sorular

x/y=null ile x/y=0,0 ürün açısından gerçekten aynı mı? Kod “flow view'da indistinguishable” diyor (ops.ts:115-121), fakat bunun bütün üç görünüm ve API sözleşmesi için ürün kararı olup olmadığı repo kodundan çıkarılamıyor. Bu, strict inverse contract'ı belirler.

Exact historical time-travel ne kadar süre garanti edilecek? Bugünkü stateAt(seq), revert ve branch yapısı geçmişin korunmasını ima ediyor; ancak “sonsuz retention” ürün kararı koddan kanıtlanamıyor. History epoch/compaction ancak bu kararla şekillendirilebilir.

Commit JSON dışarı export edilip üçüncü taraf tüketicilere veriliyor mu? Repo içindeki consumer'ları görebiliyorum; harici entegrasyonların raw ops JSON shape'ine bağımlı olup olmadığını bilemem. V1 rollout/rollback penceresi buna göre sertleşebilir.

Audit için cryptographic tamper-evidence isteniyor mu? rebuildCheck() bunu sağlamıyor. Eğer hukuki/denetimsel audit gereksinimi varsa prevHash/eventHash/historyEpoch benzeri ayrı bir karar gerekir; bunu yalnız mevcut koda bakarak gerekli ilan etmiyorum.
